# Apple input audit for passive fueling predictions

Checked October27, 2026 against Apple documentation, the installed iPhoneOS27.1 SDK headers, Fuel Up's native collector and the frozen research export. This is an API and code audit, not a claim that additional collection has been deployed or physically validated. No new permissions were requested and no new personal data sources were enabled.

**There are additional useful public signals, but no general iPhone API found that gives Fuel Up a connected car's fuel gauge, odometer or full-tank confirmation.** The most promising near-term work is better use of existing quality/activity evidence plus audio transitions and location-service diagnostics.

## Already collected: use these before adding new sensors

| Existing input | Evidence in this snapshot / code | Next useful derived feature |
|---|---|---|
| GPS position, speed, travel course, timestamps | 59,552 location events; sensor and receipt time kept separately | Approach consistency, speed changes, true time ordering, short-gap coverage |
| Speed and direction uncertainty | `speedAccuracy` on all 59,552; `courseAccuracy` on 52,766 | Downweight unreliable heading/speed matches; current route replay uses course but not its uncertainty |
| Altitude and vertical uncertainty | Both on 44,551 locations | Reject implausible vertical changes; weak optional grade/parking context, not a fuel measurement |
| Source provenance | `simulated` and `accessory` fields on all location events | Source-aware confidence; accessory-provided GPS does not identify the driver or give fuel level |
| Live motion categories and confidence | 70,305 motion events | Automotive-to-stationary-to-walking-to-automotive patterns; driver/passenger remains unresolved |
| Recovered motion history | 1,498 diagnostic chunks | Identify unmeasured driving while the app was suspended; never turn motion duration into known miles |
| Step history and visit walking | 12,296 step-history diagnostic chunks; 643 visits with steps and walking distance | Split short walking around a car from a longer store visit; use only after the data becomes available |
| Apple general visits and station visits | 608 general-visit diagnostic events; 117 `system_visit` events | Independent dwell/arrival corroboration and routine-place history |
| Audio output type | 128,072 context snapshots contain output port types | Existing `CarAudio`/Bluetooth observations combined with motion, not proof of a specific car or driver |
| Phone charging, battery, low-power, thermal, uptime, foreground state | `DrivingResearchPacketContext.swift` | Confidence degradation and reboot/collection boundaries; charging alone is not a car connection |
| Connectivity | `NWPathMonitor` already records available/Wi-Fi/expensive/constrained flags | Separate delayed upload from missing sensor capture |
| Own-app opens, selection, navigation and map actions | Already recorded in packet context | Intent feature when it exists; no navigation action was available in the tested five-minute pre-purchase windows |

Counts above mean field presence, not that every value is valid or every event independent. The current ML experiment uses only a subset of these signals; adding the rest is feature engineering on existing evidence, not a new permission flow. Native source files are under `modules/fuel-up-driving-activity/ios/Research/`: `DrivingResearchCollector.swift`, `DrivingResearchPacketContext.swift`, `DrivingResearchTimingHistory.swift`, `DrivingResearchStepHistory.swift`, `DrivingResearchCrossChecks.swift`, and `DrivingResearchMileage.swift`.

## Additional public inputs with no manual form entry

| Input | What Apple provides | Access / current status | Likely usefulness and limits |
|---|---|---|---|
| **Audio-route change events** | Previous/current route and reason via `AVAudioSession.routeChangeNotification` | Current code samples the route but has no dedicated change-event listener. No microphone recording needed. | Timestamp possible car entry/exit more precisely while the app can receive events. This is the app's observable audio route, not an unrestricted paired-car inventory or guaranteed background wake source. [Apple](https://developer.apple.com/documentation/avfaudio/avaudiosession/routechangenotification) |
| **Modern location diagnostic stream** | Stationary flag, unavailable location and authorization/session diagnostics through `CLLocationUpdate`/`CLServiceSession` | Collector currently uses `CLLocationManager`, its errors and pause/resume delegates. A modern session path needs lifecycle testing under existing grants. | Explain why fixes stopped; improve gap confidence and recovery. Does not promise continuous GPS or reconstruct missing distance. [Updates](https://developer.apple.com/documentation/updates/corelocation), [diagnostics](https://developer.apple.com/documentation/corelocation/clservicesessiondiagnostic) |
| **Recorded accelerometer** | `CMSensorRecorder`: requested 50Hz recording up to 12h, retained up to 3 days, including suspension/termination | Not implemented. Check support and Motion authorization; recording must be started in advance. | Candidate for trip/stop transition evidence during gaps. Sample volume, energy and phone handling confounds require a bounded on-device experiment. It cannot recover old recordings never requested, and integrating acceleration is not a trustworthy car odometer. [Recording](https://developer.apple.com/documentation/coremotion/cmsensorrecorder/recordaccelerometer%28forduration%3A%29), [history](https://developer.apple.com/documentation/coremotion/cmsensorrecorder/accelerometerdata%28from%3Ato%3A%29) |
| **Device motion / gyro / magnetometer** | Gravity-separated acceleration, rotation, attitude and calibrated magnetic field | `CMMotionManager` not used by the research collector; ordinary live operation is subject to app execution limits | Could detect handling/entry/exit or turns. Phone orientation and movement dominate; do not interpret engine vibration or pumping as established labels. Prefer short event-focused windows. [Apple](https://developer.apple.com/documentation/coremotion/cmmotionmanager) |
| **Pedometer cadence, pace, pause/resume events** | `CMPedometerData` and `CMPedometerEvent`; walking history | Steps/distance already collected; historical average active pace is recorded in step-history chunks. Live cadence/pause/resume not used. Check platform support/authorization. | More precise walking-around-car versus shopping evidence. Pedometer distance is walking/running, not vehicle travel. [Data](https://developer.apple.com/documentation/coremotion/cmpedometerdata), [manager](https://developer.apple.com/documentation/coremotion/cmpedometer) |
| **Barometric altitude** | `CMAltimeter` relative/absolute altitude on supported hardware | Not implemented; Motion authorization/support checks required | Small additional vertical-motion context; likely low value compared with existing GPS altitude. No tank-pressure reading. [Apple](https://developer.apple.com/documentation/coremotion/cmaltimeter/authorizationstatus%28%29) |
| **Road distance, ETA, route geometry** | `MKDirections`, ETA response, route/steps | App already has a MapKit routing module; not part of the historical ML features. Network requests to Apple are needed for new routes. | Better candidate accessibility and approach than a simple 300m circle. Cache/bound candidate requests; route suggestions do not prove the route actually driven. [ETA](https://developer.apple.com/documentation/mapkit/mkdirections/etaresponse), [directions](https://developer.apple.com/documentation/mapkit/mkdirections) |
| **Current Wi-Fi association** | SSID/BSSID/security of the currently joined network via `NEHotspotNetwork.fetchCurrent` | Requires Access Wi-Fi Information entitlement and a qualifying condition such as precise-location authorization. Not currently collected. | Could identify a previously known vehicle hotspot, but it is a weak optional signal. No all-nearby-network history. Prefer on-device derivation and avoid uploading network identifiers. [Apple](https://developer.apple.com/documentation/networkextension/nehotspotnetwork/fetchcurrent%28completionhandler%3A%29) |
| **Weather** | WeatherKit temperature, wind and conditions for a location | Additional WeatherKit capability/service use; no manual form, but a network source | Possible consumption covariates once a genuine fuel/vehicle target exists. Will not resolve missing refill labels or tank capacity now. [Apple](https://developer.apple.com/documentation/weatherkit/currentweather) |

## Available only with meaningful additional access or setup

| Route | What it could add | Why it is not a silent drop-in |
|---|---|---|
| **CarPlay app connection** | Connection lifecycle and explicit interactions with our app in the car | Apple supports fueling apps, but requires the appropriate CarPlay entitlement and integration. A CarPlay connection does not itself expose arbitrary vehicle telemetry. [CarPlay](https://developer.apple.com/carplay/), [entitlements](https://developer.apple.com/documentation/carplay/requesting-carplay-entitlements) |
| **BLE / MFi vehicle accessory** | Data the particular accessory exposes; potentially actual vehicle readings with an appropriate adapter/protocol | Bluetooth permission, compatible hardware and connection setup. Core Bluetooth's connected-peripheral query matches specified services, not all paired car stereos. MFi protocols require supported accessories. Fuel/odometer availability depends on the vehicle/device, not an Apple guarantee. [Core Bluetooth](https://developer.apple.com/documentation/corebluetooth/cbcentralmanager/retrieveconnectedperipherals%28withservices%3A%29), [External Accessory](https://developer.apple.com/documentation/externalaccessory/) |
| **FinanceKit** | Eligible account transactions: merchant, category, amount and transaction date | Managed entitlement, eligible financial-management app, organization account and user financial-data authorization. US coverage is specified for Apple Card/Cash/Savings, not every card in Wallet. Fuel Up should not assume eligibility. Merchant transactions can include snacks/holds; amount alone is not gallons or a full tank. [Eligibility](https://developer.apple.com/financekit/), [fields](https://developer.apple.com/documentation/financekit/transaction/merchantname) |
| **SensorKit** | Approved research access to visits, motion, device-usage and other selected signals | Apple-approved research proposal/entitlement and granular user permission. Not unlocked merely because our UI says Research. [Apple](https://developer.apple.com/documentation/sensorkit/configuring-your-project-for-sensor-reading) |
| **Calendar** | Appointment time/destination as a route prior | Full calendar access is a new user permission. Sensitive, weak indirect evidence; unnecessary as the next step. [Apple](https://developer.apple.com/documentation/eventkit/ekeventstore/requestfullaccesstoevents%28completion%3A%29) |
| **HealthKit / Watch workouts** | Authorized workout activity and routes | Separate HealthKit authorization and health/fitness use case. Workout distance is not a hidden car odometer. A Watch companion would require installation and additional integration. [Routes](https://developer.apple.com/documentation/healthkit/reading-route-data), [authorization](https://developer.apple.com/documentation/healthkit/authorizing-access-to-health-data) |
| **Journaling Suggestions** | Information in a suggestion explicitly selected by the user | Picker-mediated sharing; not a passive background feed of the phone's private place history. [Apple](https://developer.apple.com/documentation/journalingsuggestions) |
| **UWB / iBeacon / NFC** | Proximity to participating devices, beacons or tags | Requires appropriate infrastructure, accessory configuration and permissions or interaction. Not a universal gas-pump detector. NFC background tag handling opens an app after a user taps the notification. [Nearby Interaction](https://developer.apple.com/documentation/nearbyinteraction/), [NFC](https://developer.apple.com/documentation/corenfc/adding-support-for-background-tag-reading) |
| **Receipt / pump-display OCR** | Text and potentially quantity from an available image using Vision | Requires a photo, camera access or user-selected image; therefore more interaction than this request aims for. No silent camera observation. [Apple](https://developer.apple.com/documentation/vision/vnrecognizetextrequest) |

## Misleading names and unavailable shortcuts

- `INGetCarPowerLevelStatusIntentResponse.fuelPercentRemaining` is a response **our app supplies** after obtaining vehicle data. It does not let Fuel Up query arbitrary cars through Siri. [Apple's response-object documentation](https://developer.apple.com/documentation/intents/ingetcarpowerlevelstatusintentresponse).
- `CPRouteDetail(fuelLevel:)` displays an estimate supplied by the app; it does not fetch that value from a car. [Apple](https://developer.apple.com/documentation/carplay/cproutedetail/init%28fuellevel%3A%29).
- `CMOdometerData` is documented and declared as **workout** data. It is not a vehicle CAN/OBD odometer API. [Apple](https://developer.apple.com/documentation/coremotion/cmodometerdata).
- `CLLocationManager.requestHistoricalLocations` exists, but the installed public SDK explicitly marks it `API_UNAVAILABLE(ios)`, available on watchOS9+, with a wilderness-safety entitlement and user prompt. It cannot fill our iPhone GPS gaps. Header verified at `CoreLocation.framework/Headers/CLLocationManager.h:835–873`; [API reference](https://developer.apple.com/documentation/corelocation/cllocationmanager/requesthistoricallocations%28purposekey%3Asamplecount%3Acompletionhandler%3A%29).
- CarKey has its own entitlement and vehicle integration; it is not a universal fuel-data connection. [Apple](https://developer.apple.com/documentation/carkey).
- No suitable public iPhone API was found in this audit for importing Apple Maps' private navigation/parked-car history, Significant Locations history, all Wallet purchases, another app's notifications, or arbitrary messages/mail as passive fueling labels. Do not build around private frameworks or assume cross-app access. The documented FinanceKit and Journaling paths above have explicit access boundaries.

## Recommended order

1. **Use existing uncertainty and transition history first.** Add speed/course uncertainty, source validity, motion transitions and audio presence to chronological experiments. Treat recovery information as available only at receipt; no retroactive advantage in an advance prediction.
2. **Add explicit audio transition and location diagnostic events next.** These target concrete current weaknesses: trip boundaries and unexplained GPS gaps. Keep them within existing consent and authorization, and measure battery/runtime behavior before release.
3. **Evaluate bounded motion recording only if gap diagnostics show it adds something.** Start with on-device aggregate features, not a permanent 50Hz raw upload stream.
4. **Use cached MapKit route/ETA evidence for a small candidate set.** It may reduce geometrically close but inaccessible station matches; assess it prospectively since live traffic cannot be reconstructed from our old replay.
5. For actual miles **since a full tank**, eventually require a genuine full-tank anchor or authenticated vehicle/transaction integration. Phone-only signals can estimate travel and likely purchases; none of the additional ordinary sensors establishes a complete fill.
